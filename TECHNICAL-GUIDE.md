# Technical Guide

This guide is for developers and site administrators responsible for the Foundation Events website's code, GitHub configuration, build process, and deployment.

For routine wording, event, image, and contact-information updates, use the [Non-Technical Content Guide](NONTECHNICAL-GUIDE.md) instead.

## Requirements

- Git
- Ruby 3.3 or a compatible Ruby version
- Bundler 2.3.25, as recorded in `Gemfile.lock`

Install project dependencies:

```powershell
bundle install
```

## Local development

Build the production version of the site:

```powershell
$env:JEKYLL_ENV = "production"
bundle exec jekyll build
```

Serve the site locally with production URLs and configuration:

```powershell
$env:JEKYLL_ENV = "production"
bundle exec jekyll serve
```

Open `http://localhost:4000`. Jekyll writes the generated site to `_site/`; never edit that folder because it is rebuilt and ignored by Git.

## Repository architecture

| Location | Responsibility |
|---|---|
| `_config.yml` | Jekyll configuration, plugins, exclusions, and default layouts |
| `_data/events.yml` | Event navigation, featured event, shared contact details, and social links |
| `_layouts/` | Page shells and layout hierarchy |
| `_includes/` | Reusable Liquid/HTML components |
| `Events/` | Event Markdown pages and event-specific front matter |
| `Legal/` and root Markdown files | Standard content pages |
| `Assets/` | Published images and SVGs |
| `general.css`, `nav.css` | Global presentation and navigation/footer styles |
| `config.js`, `Helper.js`, `Countdown.js` | Browser-side configuration and behavior |
| `.github/workflows/` | Build, validation, link checking, linting, and Lighthouse CI |

The site uses Jekyll's layout hierarchy:

```text
default.html
  -> page.html
       -> event.html
```

`default.html` creates the document, header, main region, footer, and scripts. `page.html` adds the heading and optional hero. `event.html` adds countdown, registration, sponsors, and previous-event sections.

## Content model

### Event pages

Every event page uses `layout: event`. Its important front-matter fields are:

| Field | Purpose |
|---|---|
| `permalink` | Canonical path; use hyphenated, trailing-slash URLs |
| `redirect_from` | Legacy URLs that redirect to the canonical URL |
| `title`, `heading`, `description` | Page heading and SEO metadata |
| `og_title`, `og_description`, `og_image` | Social-sharing metadata |
| `data_page` | Unique identifier for homepage feature selection |
| `event_datetime` | ISO 8601 event start datetime; drives countdown and JSON-LD |
| `countdown_label` | Human-readable replacement for the raw datetime |
| `registration` | Markdown rendered in the registration section |
| `sponsors`, `previous_events` | Image-gallery data |

Use `event_datetime` with an explicit timezone offset, for example:

```yaml
event_datetime: "2026-10-31T19:00:00-04:00"
```

`countdown_datetime` remains a legacy alias. Do not set both unless deliberately verifying compatibility.

### Shared data

`_data/events.yml` provides:

- `events`: navigation and homepage event order;
- `next_event`: the `data_page` value of the highlighted event, or `""` to list all events;
- `contact`: footer, contact page, and structured-data organization fields;
- `social`: social links displayed in the footer and Contact Us page.

Keep YAML indentation consistent. Update `contact.phone` for display and `contact.phone_tel` with an E.164-style, digits-only callable number.

## URLs, metadata, and structured data

- Site-wide canonical base URL: `_config.yml` → `url`.
- `<head>` metadata and canonical/Open Graph/Twitter tags: `_includes/head.html`.
- Event JSON-LD: `_includes/event-schema.html`.
- Sitemap: generated by `jekyll-sitemap`.
- Redirects: generated by `jekyll-redirect-from`.
- `robots.txt`: a Jekyll-rendered source file at the repository root.
- Security contact: `security.txt`, built to `/.well-known/security.txt`.

When adding a real event from `Events/Event Template.md`, change `sitemap: false` to `sitemap: true`; templates must remain excluded from search engines.

## Client-side code

`config.js` is the shared ES module configuration.

- `Helper.js` applies an image fallback and marks the active navigation link.
- `Countdown.js` reads `#countdown-date[datetime]`, updates `#countdown`, and honors `prefers-reduced-motion`.
- `_includes/scripts.html` conditionally loads `Countdown.js` only for pages with `event_datetime` or the legacy `countdown_datetime`.

Use DOM-safe APIs (`textContent`, attribute setters) and retain the module loading pattern. Validate changed JavaScript before committing:

```powershell
node --check config.js
node --check Helper.js
node --check Countdown.js
```

## Validation

Install the local command dependencies once after cloning or pulling a changed `package.json`:

```powershell
npm install
```

Install [Lychee](https://github.com/lycheeverse/lychee#installation) separately and ensure `lychee` is on `PATH`. It checks links in the built site and is the same tool used by GitHub Actions. The Lighthouse command also requires Google Chrome or Chromium to be installed. If it is not auto-detected, set `CHROME_PATH` to the browser executable before running the command.

Run these commands from the repository root:

| Command | What it checks |
|---|---|
| `npm run lint` | JavaScript, CSS, and Markdown style rules |
| `npm run link-check` | Markdown links and links in the generated site |
| `npm run validate` | Production build plus local HTML validation |
| `npm run lighthouse` | Full local Lighthouse audit: Navigation + Snapshot mode, Mobile + Desktop, all categories |
| `npm run lighthouse:ci` | Exact reproduction of the `lighthouse.yml` CI check (single Navigation/mobile pass, 3 runs averaged) |
| `npm run build` | Production Jekyll build only |

`link-check`, `validate`, and `lighthouse*` build the site before running their respective checks. Run the smallest applicable command while developing, then run the appropriate full check before opening a pull request.

### About the two Lighthouse commands

- **`npm run lighthouse:ci`** calls `@lhci/cli` with `.github/lighthouserc.json` -- the same config CI uses. That config sets `numberOfRuns: 3`, which means each URL is audited **three times and the median result is reported**, purely to reduce run-to-run flakiness in performance metrics. It is a repeat of one configuration (Navigation mode, mobile emulation), not three different modes or devices.
- **`npm run lighthouse`** runs `scripts/lighthouse-report.mjs`, a small script built on Lighthouse's "User Flow" API (`@lhci/cli` cannot do this -- it only supports a single Navigation-mode pass per config). For every URL in `.github/lighthouserc.json`, it audits:
  - **Navigation mode** (a full page load) and **Snapshot mode** (a point-in-time DOM snapshot), matching the "Mode" selector in the Chrome DevTools Lighthouse panel.
  - Both **Mobile** and **Desktop** device emulation.
  - All default categories: Performance, Accessibility, Best Practices, and SEO (the `pwa` category was removed in Lighthouse 12+; the DevTools panel's "Agentic browsing" checkbox is a DevTools-only experimental feature not exposed through Lighthouse's public API, so it is not included here).

  It writes one combined HTML report per page per device (containing both the Navigation and Snapshot steps) to `.lighthouse-reports/` (git-ignored) and prints a score summary table to the console. Performance metrics such as LCP/CLS/TBT are not applicable during the Snapshot step -- that mirrors Chrome DevTools' own behavior, since Snapshot mode does not capture page-load timing.

On PowerShell, set a nonstandard Chrome location for the current terminal with:

```powershell
$env:CHROME_PATH = "C:\Path\To\chrome.exe"
```

Run a production build directly after changing templates, data, configuration, Markdown front matter, JavaScript integration, or dependencies:

```powershell
npm run build
```

The `validate` command uses HTML Proofer. On Windows, it requires `libcurl` to be available to the Ruby runtime:

```powershell
npm run validate
```

GitHub Actions provide these checks:

| Workflow | Purpose |
|---|---|
| `validate.yml` | Production Jekyll build, sitemap/robots checks, and HTML Proofer |
| `link-check.yml` | Markdown and built-site link checks; runs weekly too |
| `lint-format.yml` | Super-Linter execution |
| `lighthouse.yml` | Lighthouse performance, accessibility, and SEO analysis |

Review all pull-request checks before merging. For a failed GitHub Action, open the failed job, identify the first actionable error, make a narrow fix, and push a new commit to the pull-request branch.

## Deployment and rollback

The repository is deployed through GitHub Pages. A merge to `main` triggers the configured GitHub workflows and deployment process.

Use pull requests for all changes:

1. Branch from current `main`.
2. Keep the change focused.
3. Run the applicable local checks.
4. Open a pull request and wait for required checks.
5. Merge only after reviewing the rendered change and workflow results.

If a deployed change must be undone, use GitHub's **Revert** action on the merged pull request, review the generated revert pull request, and merge it after checks pass. Do not edit generated `_site/` files or force-push `main`.

## Troubleshooting

| Symptom | Likely cause and response |
|---|---|
| Build fails on a new page | Check YAML front-matter delimiters, indentation, quotes, and Liquid syntax. |
| Image is missing | Verify case-sensitive filename and the `/Assets/...` path. Build output URLs percent-encode spaces automatically. |
| Event is absent from nav/homepage | Add it under `events` in `_data/events.yml`; ensure `page` matches its `permalink` without the trailing slash. |
| Wrong featured event | Ensure `next_event` exactly matches the event page's `data_page`. |
| Countdown is absent | Set `event_datetime` to a valid ISO 8601 datetime with timezone offset. |
| Page is not indexed | Check `robots`, `sitemap`, and whether `sitemap: false` was copied from a template. |
| Local HTML Proofer fails before checking pages | On Windows, ensure `libcurl` is installed and on `PATH`; CI remains the authoritative validation environment. |

## Maintenance boundaries

Do not commit generated output (`_site/`), Jekyll caches (`.jekyll-cache/`), credentials, tokens, or production secrets. Dependency updates should modify both `Gemfile` and `Gemfile.lock` together and be validated with a production build.
